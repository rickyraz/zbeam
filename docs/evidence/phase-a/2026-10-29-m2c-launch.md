# M2c owned launcher — 2026-10-29

`TwoWorkerLaunch` starts only an owned guardian/native pair and waits for the
native registration line. Its caller supplies a fixed peer atom; no atom is
created on restart. A bounded loopback EPMD lookup waits for a previous
registration to disappear. Already-connected peers and occupied names reject
startup without deliberately attaching to or killing the existing service.
The caller must exclusively own that configured name and peer connection; this
is not a defense against malicious local races or node impersonation.

Linux/WSL, Elixir 1.20.4 / OTP 29: three tests passed in 30 fresh VMs, covering
actual two-worker discovery, cleanup and reuse, occupied-name isolation and
startup failure. Debug/safe `zig build test-worker-recovery` each passed 5/5
steps, including the launcher, admission, M1 owner and M2b process-loss tests.
The initial fixture had an Elixir compile error from variables bound inside an
assertion; it was corrected and both logs are retained.

The launcher is an internal primitive, not the M2c owner. The caller owns the
Port, traps exits and closes it; OS-level cleanup remains the existing guardian
contract. Rollback removes helper/tests and their recovery hook. No native wire
or M1 behavior changes; no TLS/secret or foreign process-tree guarantee is added.
