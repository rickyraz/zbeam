# snmalloc Branch Experiment

- Date: 2026-09-27; branch `explore/snmalloc`, based on standard-baseline commit `27b0fee`.
- Upstream: `526c55bdffa17aae20a9a3d24fe68a7a3b8d9894` (0.7.5), clean checkout.
- Environment: Zig 0.16.0, native Linux x86-64 GNU ABI on WSL2; four visible CPUs; OTP 28/Elixir 1.19.5 benchmark VM, two schedulers.
- Decision: **do not promote snmalloc to the default**. Retain the experiment for measured cross-thread/large-buffer workloads; memory and representative-workload gates are not met.

## Integration actually tested

The optional executable/lab adapter uses the upstream malloc-only, namespaced C shim. `zig c++` compiled it with C++20, O3, no exceptions, pthread TLS cleanup and 128-bit compare/exchange support. No CMake, additional compiler installation, vendored dependency or global malloc/new override was needed. The resulting object links against libc without a C++ runtime library in this configuration; other targets are unverified.

`-Dsnmalloc-object=... -Dallocator=snmalloc` enables the adapter. With no object supplied, default builds retain the previous dependency path. The batteries never import the adapter. The shim-build script checks the source revision, clean checkout and absence of global allocation-override symbols.

Three variants were tested:

1. **sn-basic:** aligned allocation, unsized free, conservative no-resize/no-remap.
2. **sn-resize:** additionally permits in-place logical resize/remap within the pinned backend's reported physical capacity. It never invokes moving C realloc; unsized free retains physical size-class identity.
3. **sn-checks:** the same capacity-reuse adapter with `SNMALLOC_CHECK_CLIENT` enabled in the C++ object. This is upstream hardening, not ASAN/TSAN or proof of Zig-wide memory safety.

Fresh SMP/libc controls linked the same normal shim object, held libc/process initialization constant and did not select snmalloc for application allocations. Object recipes, compiler identity, flags, hashes and undefined symbols are in [normal object provenance](2026-09-27-allocators/verification/snmalloc-object.txt) and [checks provenance](2026-09-27-allocators/verification/snmalloc-checks-object.txt).

## Verification

All five ReleaseSafe variants passed **10/10 allocator/workload checks**. The snmalloc-specific checks cover alignment from 1 to 65536 bytes, zero/non-multiple lengths, data preservation across growth, oversized failure retaining ownership, in-place capacity boundaries, late free after 64 producer-thread exits, and real `Io.Group` cancellation.

The selected allocator also backs the actual socket pause/resume/cancellation oracle. A single receiver-side counter is inspected only after tasks join; all logical allocated bytes are freed. Ordinary core tests continue using `std.testing.allocator` rather than silently losing its diagnostics.

Full Debug (normal shim + resize) and ReleaseSafe (checks shim + resize) gates passed **57/57 tests plus CLI regression**. Real OTP **25/26/27 passed both handshake roles** with the checks variant. Logs: [Debug](2026-09-27-allocators/verification/snmalloc-debug.log), [ReleaseSafe/checks](2026-09-27-allocators/verification/snmalloc-release-safe-checks.log), [OTP](2026-09-27-allocators/verification/snmalloc-checks-otp.log).

The first direct C++ build exposed a required CMake-defined wait-on-address macro; the recipe now sets it explicitly. The first Zig wiring attempt duplicated an options source module; sharing one module fixed it. Neither failed attempt contributes performance evidence.

## Measured results

The same predeclared five-repetition, three-payload matrix produced **225 completed runs and 1,050,000 raw samples**. Percentiles were recomputed from every raw sample set. Lab medians first aggregate the three correlated cycles within each launch; the reported values are medians across five launches.

The capacity-reuse variant improves the isolated 64 KiB echo loop (7472.2 operations/s versus libc's 6214.6 and SMP's 2113.4). Its network throughput at that size is only about 0.7% above libc. At 32 B, network differences are small; there is no general service-throughput win.

Cross-thread results are workload-dependent. At 4 KiB, sn-resize achieved 127347.8 handoffs/s versus libc's 103320.9, but retained 4248 KiB after idle versus 3540 KiB. At 64 KiB, sn-resize retained 14164 KiB versus libc's 3788 KiB after the same 100 ms idle interval. Its peak HWM was 14164 KiB versus libc's 14276 KiB: the important distinction is retained versus peak memory, not an assertion that every memory metric regressed equally.

### Gate assessment

- **Correctness checks run here:** passed. This is not all-platform or production proof.
- **Representative performance:** mixed. Some isolated/large/cross-thread cases improve; small network workloads do not meet a consistent 10% advantage over the existing standard choices.
- **Tail latency:** sn-resize's 32 B handoff p99 was 198767 ns versus SMP's 179967 ns and libc's 162025 ns; the predeclared 5% no-regression gate is not met on these medians.
- **Memory:** the predeclared 10% peak/post-idle budget is not met. Hardening's observed large-message speed does not cancel its larger RSS.
- **Lifecycle:** late frees and cancellation passed. Short retained-memory measurements do not prove a leak, long-term plateau or reclamation after prolonged idle.

The experiment does not justify changing the default. If a real service later exhibits a relevant remote-free bottleneck, investigate explicit idle/thread-pool reclamation and its latency cost in another branch rather than dismissing retained memory as irrelevant. No such reclamation hook was added here.

## Reproduction and limits

```sh
sh scripts/bench/build_snmalloc.sh /path/to/pinned/checkout /tmp/snmalloc.o normal
sh scripts/bench/build_snmalloc.sh /path/to/pinned/checkout /tmp/snmalloc-checks.o checks
zig build test-all test-allocators -j2 -Dallocator=snmalloc -Dsnmalloc-object=/tmp/snmalloc.o -Dsnmalloc-resize=true
zig build -j2 -Doptimize=ReleaseSafe -Dallocator=snmalloc -Dsnmalloc-object=/tmp/snmalloc.o -Dsnmalloc-resize=true -p /tmp/sn-resize
zig build build-allocator-bench -j2 -Doptimize=ReleaseSafe -Dallocator=snmalloc -Dsnmalloc-object=/tmp/snmalloc.o -Dsnmalloc-resize=true -p /tmp/sn-resize
```

Prepare the other four prefixes with the corresponding allocator/object/resize choices, then use `scripts/bench/allocator_matrix.py` with all five labeled prefixes. The object path itself is trusted local build input; the recipe, hashes and tests establish the artifact used here, not a general package-verification system.

Unverified: native-host replication outside WSL2, upstream debug builds, real OS memory-pressure failure, sanitizer campaigns, useful native jobs, long soaks, additional platforms, TLS/deadlines and concurrent peer servicing. OOM coverage uses the adapter's oversized-request rejection and injected allocation failures; it is not a claim that the OS cannot kill a process under pressure.
