# Bounded independent-job batches

**Status:** implemented and compatibility-tested research contract; performance promotion is not established.

## Contract

`batch` and `serve-batch` expose one synchronous `sha256_batch` worker. A request is `{Session, ID, Jobs}`: a 16-byte binary session, sequential nonnegative i32 ID starting at zero, and 1–32 independent binaries with aggregate bytes at most 1 MiB. Reply: `{Session, ID, concatenated_32_byte_digests}`. Frame cap: 2 MiB; one frame outstanding. The session/ID state is per connection. Duplicate/gapped IDs, session changes, excessive counts/bytes and invalid terms disconnect that peer. Reconnect starts fresh state; clients must choose a new unpredictable session and match both fields. There is no global session registry, deduplication or replay guarantee. ID exhaustion requires a new connection/session.

This batches separate hashes, not one hash over concatenated input. Demand is restored only after processing/reply, and finite I/O deadlines remain active. The registered-message subset does not implement `gen_server:call`, process links or remote monitors. The runtime composes ETF/protocol/transport/actor without changing the battery DAG.

## Performance controls and reproduction

The optional raw Port, ETF Port and dirty-CPU NIF all compute the same independent hashes. The NIF accepts a prepacked binary of equal-sized jobs without ETF; raw Port length packing and ETF encoding are timed. Every path uses preformed jobs, one outstanding batch, exact-result comparison, 100 warmups, batch completion latency and jobs/second. Batch completion latency is not divided by job count. Application fill wait is excluded; callers must include it before claiming request-tail improvement.

```sh
zig build test-all test-research build-research -j2 -Doptimize=ReleaseSafe
zig build test-interop-docker -j2 -Doptimize=ReleaseSafe
(cd benchmarks/zigler && export ZIG_EXECUTABLE_PATH="$(command -v zig)" \
  ERL_FLAGS='+S 2:2 +SDcpu 2 +SDio 1'; mix deps.get && mix test)
python3 scripts/bench/batch_matrix.py /new/output/directory
```

The matrix uses ten fresh-VM repetitions, seeded per-repeat ordering, 1/8/32 jobs, 32/4096/32768 bytes per job and 1000 measured batches per launch. It records raw samples, binary/dependency hashes, CPU ticks and RSS at completion/100 ms/1 s; RSS observations are not peaks and include BEAM plus native child for external paths. Paired run-level bootstrap intervals accompany comparisons to each control. Threaded NIFs are excluded as unresolved, not defeated.

Native Linux replication, loaded-BEAM fairness, application fill-wait, complete memory/cancellation promotion gates and a demonstrated advantage over equally batched NIF/Port remain open.
